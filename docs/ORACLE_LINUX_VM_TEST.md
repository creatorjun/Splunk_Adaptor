# Oracle Linux VM 검증 결과

2026-10-08에 제공된 테스트 VM에서 GitHub 저장소를 내려받아 Docker 이미지를 직접 빌드하고 프로그램을 실행했습니다. 최초 구현의 애플리케이션 소스와 테스트 스크립트 기준 커밋은 `9501b4cc661982b1c9e40f42e9b01211b68c7ad1`입니다. 이후 추가한 분별 그래프 검증은 문서 하단에 별도로 기록했습니다.

## 확인한 환경

| 항목 | 실제 확인값 |
|---|---|
| OS | Oracle Linux Server 8.10, x86_64 |
| 커널 | UEK `5.15.0-206.153.7.1.el8uek.x86_64` |
| Docker Engine | 26.1.3 |
| Docker Compose | 2.27.0 |
| 컨테이너 Java | Temurin 21.0.12.1 |
| SELinux | Disabled |
| 프로젝트 경로 | `/opt/Splunk_Adaptor` |
| 경고 파일 경로 | `/opt/Splunk_Adaptor/warn` |
| 관리 화면 바인딩 | `127.0.0.1:8080` |

VM에는 Docker가 설치되어 있지 않아 Docker CE의 EL8 패키지와 Compose 플러그인, Git을 설치하고 Docker 서비스를 시작했습니다. Docker 설치 절차는 [Docker의 RPM 저장소 안내](https://docs.docker.com/engine/install/centos/)를 참고했습니다. 설치 시 확인한 Docker GPG 키 지문은 `060A 61C5 1B55 8A7F 742B 77AA C52F EB6B 621E 9F35`입니다. 이 문서는 위 조합의 실행 결과를 기록하며 다른 OS·커널·Docker 버전의 지원을 보장하지 않습니다.

## 빌드 및 자동 테스트

VM의 Docker 빌드 단계에서 `mvn verify`가 성공했습니다. 자동 테스트 **19개**, 실패 **0개**, 오류 **0개**, 생략 **0개**입니다. 초기 호스트에는 Java와 Maven을 별도로 설치하지 않았습니다.

도메인 임계치 판정, 애플리케이션 설정·저장 실패 처리, 파일 저장, Linux 수집, HTTP API, 아키텍처 의존 방향 검사를 모두 통과했습니다.

| 항목 | 호스트 / 프로그램 대조 결과 |
|---|---|
| CPU | `/proc/stat` 직접 계산 4.8843%, 프로그램 4.9628% |
| 메모리 총량 | `/proc/meminfo`와 동일한 8,027,824,128 bytes |
| `/` 디스크 전체 용량 | `statvfs`와 동일한 27,393,159,168 bytes |
| `/var` 디스크 전체 용량 | `statvfs`와 동일한 27,393,159,168 bytes |

CPU는 프로그램 측정 직후 호스트 카운터를 읽어 다음 측정 구간과 대조했습니다. 읽기 시점 차이 때문에 값이 완전히 같지는 않습니다. 이 테스트에서 차이는 약 0.0785%p였습니다. 메모리 가용량과 디스크 미할당 공간도 직접 측정값과 비교했으며 검사 허용 범위 안에 있었습니다. 측정 중 가용 메모리나 디스크 공간이 바뀔 수 있으므로 총량은 정확히 대조하고 가용량에는 시간 차이를 허용했습니다.

## 동작 검사

`python3 scripts/smoke_test.py`의 여섯 가지 실제 실행 검사가 모두 **PASS**였습니다.

1. 호스트 CPU·메모리·파일시스템과 프로그램 측정값 대조.
2. CPU·메모리·디스크 임계치를 일시적으로 낮춘 뒤 재시작 없이 적용. 이번 검사에서는 약 **0.346초** 후 도달 이벤트를 확인했습니다.
3. `cpu`, `memory`, `disk:/`, `disk:/var` 각각의 도달 JSON **4개** 생성. 각 파일에 CPU 수치, 메모리 수치, 디스크 2개 및 임계치가 포함됨.
4. 메모리 재알림 주기에 따라 추가 JSON **1개** 생성. 복구 이벤트는 로그에 기록되고 추가 경고 파일을 만들지 않음.
5. 오래된 설정 버전으로 저장을 요청하면 HTTP **409** 반환.
6. 원래 설정으로 복원한 뒤 모니터 컨테이너를 재시작하여 설정과 경고 파일 보존 확인.

JSON 파일 5개는 검사 증거로 프로젝트의 `warn/`에 보존했습니다. 운영 설정은 기본 CPU 80%, Memory 85%, Disk 90%, 측정 주기 5초, 재알림 300초로 복원했습니다. 검사 중에는 자원 부하를 인위적으로 높이지 않고 임계치를 낮춰 이벤트 생성을 확인했습니다.

## 최종 상태

- Docker health 상태: `healthy`.
- `/health`: HTTP 200, `{"status":"UP"}`.
- 관리 화면 `/`: HTTP 200.
- 실행 사용자: `10001:10001`.
- 컨테이너 루트 파일시스템: 읽기 전용.
- Linux capability: `ALL` 제거.
- `.env`: root 소유, 권한 `0600`.
- `warn/`: `10001:10001` 소유, 권한 `0750`.

VM의 SELinux가 이미 Disabled 상태였으므로 Enforcing 정책에서의 접근은 검증하지 않았습니다. 다른 커널·마운트 구성, 장기간 실행, 강제 종료·전원 장애 상황은 이번 테스트 범위에 포함하지 않았습니다.

접속 비밀번호, 관리 토큰, VM 원본 상태·JSON 파일은 저장소에 게시하지 않았습니다. 원본 검사 결과는 VM의 `verification/oracle-vm/smoke-report.json`과 로컬 검증 디렉터리에 남겼습니다.

## 1분 폴링 GUI 대시보드 추가 검증

같은 날 커밋 `17e96fc1002a276fb97f440f353b44b266ccfc6e`를 VM에 적용하여 이미지를 다시 빌드했습니다. VM과 로컬 Docker 빌드에서 자동 테스트 **27개**, 실패 **0개**, 오류 **0개**, 생략 **0개**를 확인했습니다. 추가 테스트는 분별 기록의 60초 간격, 60분 보관, 저장 실패 복구, 누락 값, 재시작 중복 방지와 파일 영속 저장을 검사합니다.

VM의 기본 실행 대상은 `multi-user.target`이며 `gnome-shell`과 `xorg-x11-server-Xorg` 패키지가 설치되어 있지 않았습니다. 서버에 데스크톱 환경을 추가하지 않고 Java 컨테이너가 웹 화면을 제공하고, 외부 PC의 Chrome에서 SSH 터널을 통해 접속했습니다. 이 검사는 GUI 패키지 없이 실행됨을 확인한 것이며 VM의 최초 설치 프로필 자체는 확인하지 않았습니다.

`python3 scripts/minute_dashboard_test.py`의 다섯 가지 검사가 모두 **PASS**였습니다.

| 검사 | 실제 확인 결과 |

| 분별 API 인증 | 토큰 없는 `/api/history` 요청은 HTTP 401 |
| 통합 그래프 | 화면에 canvas 1개, 브라우저 조회 주기 60,000ms |
| 실제 호스트 수집 | CPU·Memory·Disk 수치가 유효하며 연속 기록 간격 **60.127초** |

Chrome에서도 관리 토큰 연결 후 호스트의 실제 수치를 확인했습니다. 브라우저 자동 조회에 따라 분별 기록이 증가했고, Memory 범례를 눌러 숨김·표시 상태가 전환되는 것을 확인했습니다. 그래프를 가리키면 시각과 CPU·Memory·Disk 수치가 표시됐으며 검사 중 브라우저의 경고·오류 로그는 없었습니다.

검사 후 서비스는 `healthy`, `/health`는 HTTP 200 상태였으며 경보 설정은 CPU 80%, Memory 85%, Disk 90%, 측정 주기 5초, 재알림 300초였습니다. 기존 경고 JSON 5개가 보존됐습니다. 분별 그래프는 60초 수집과 최근 60분 보관을 사용하고 경보 판정은 설정한 주기로 별도 수행합니다.

분별 검사 원본 결과는 VM과 로컬의 `verification/oracle-vm/minute-dashboard-report.json`에 보관했습니다. 장기간의 60분 실시간 실행은 이번 VM 검사 범위에 포함하지 않았으며 60분 보관·만료 정책은 자동 테스트에서 검증했습니다.
